  ---
  RocksDB RandomSeek (Get) 与 Scan (Iterator) 详细流程

  一、核心概念与架构概览

  RocksDB 使用 LSM-Tree 架构，数据分布在：
  1. MemTable — 内存中的活跃写入缓冲（skiplist/哈希链）
  2. Immutable MemTables — 等待刷盘的只读 MemTable
  3. SST Files (L0~Ln) — 磁盘上的排序文件

  RandomSeek (Get) 是按 key 进行点查；Scan (Iterator)
  是基于迭代器的范围扫描。两者共享查询 SuperVersion（包含 mem + imm + current
  Version）的路径，但 Iterator 还额外通过 MergingIterator
  将多个数据源合并为一个有序流。

                  break;
              case kTypeDeletion:    // 记录删除
                  merge_context_.Clear();
                  last_not_merge_type = kTypeDeletion;
                  break;
              case kTypeMerge:       // 收集 Merge 操作数
                  merge_context_.PushOperandBack(iter_.value(), ...);
                  break;

          case kTypeMerge:     // 最终 merge

              return true;
          case kTypeValue:     // 有值，直接使用 pinned_value_
              valid_ = true; return true;
      }
  }

  六、优化技术总结

  1. Bloom Filter 两级过滤: Full filter（整个 SST 级别）+ Block-based
  filter（数据块级别），快速排除不存在的 key
  2. Row Cache: 在 TableCache 层缓存完整的 key→value 映射，绕过 SST 查找
  3. 哈希索引 (SeekForGet): 数据块内使用哈希表加速点查，冲突时回退到二分查找
  4. 分数级联 (FileIndexer): 上层查找结果缩小下层搜索范围
  5. Reseek 优化: 当连续跳过太多不可见版本时，直接用 Seek() 跳跃前进
  6. GetContext 状态机: 避免不必要的文件访问——kFound 后立即返回
  7. Arena 连续内存分配: 整个迭代器树在连续内存中，缓存友好
  8. Iterator Pinning: 避免数据块被释放导致迭代器失效
  9. MergeValuesNewToOld 状态机: 遇到 Merge 时收集操作数并计算最终值，与普通的
  Next/Prev 逻辑分离

  关键差异

  1. 优化路径不同

  Get() 有专属的点查询优化：
  - Row Cache (table_cache.cc:412): 缓存完整 key→value 映射，直接返回
  - SeekForGet (block.cc:276): 数据块内使用哈希索引，O(1)
  定位；只有冲突时才退化到二分查找
  - GetContext 状态机 (get_context.h): kFound 后立即跳出所有循环

  Seek() 没有这些优化：
  - 没有 Row Cache
  - 不使用 SeekForGet（因为要准备好迭代器状态以便后续 Next）
  - 使用通用的 DataBlockIter::Seek()（二分查找）
  - 必须维护 saved_key_, direction_ 等状态

  2. 资源开销不同

  Seek() 需要创建完整的迭代器树：
  - 创建 MergingIterator 堆（即使只做一次 Seek）
  - 分配 ArenaWrappedDBIter + DBIter + MergingIterator + N 个子迭代器
  - 维护 Range Delete 聚合器
  - 维护 Merge 上下文

  Get() 只需栈上分配，不需要维护迭代器生命周期。

  3. 语义差异

  即使 seek_nexts=0:

  ┌──────────────┬───────────────┬──────────────────────────────────────────┐

  │              │               │ iter->key() == key_6                     │
  ├──────────────┼───────────────┼──────────────────────────────────────────┤
  │ key_5        │ 返回 NotFound │ 定位到 key_6，iter->Valid() 但           │
  │ 从未存在     │               │ iter->key() == key_6                     │
  └──────────────┴───────────────┴──────────────────────────────────────────┘

  Seek 总是定位到 ≥target 的第一个 key，这可能与 target 不同。而 Get 严格检查
  key 是否匹配。

  4. Merge 操作处理

  Get 对 Merge 的处理：MemTable 中通过 SaveValue 的反复回调收集操作数，最终在
  Version::Get() 末尾由 MergeHelper::TimedFullMerge 统一计算。

  Seek 对 Merge 的处理：调用 MergeValuesNewToOld() 直接解析并合并，结果缓存在
  saved_value_ 中，Next() 时跳过已合并的条目。

    - Row Cache 命中 → 直接返回
    - Bloom Filter → 提前终止
    - SeekForGet (Hash Index) → O(1) 定位
    - 无状态维护开销
    - 无 MergingIterator 堆开销

    - 每次 Seek 创建 Iterator（除非 tailing iterator）
    - 使用通用的二分查找
    - 维护 saved_key_ / direction_ / merge_context_

  MergingIterator 定位到了 internal key 最小且 ≥ target

  bool DBIter::FindNextUserEntryInternal(bool skipping_saved_key, const Slice* 
  prefix) {
      current_entry_is_merged_ = false;
      uint64_t num_skipped = 0;
      bool reseek_done = false;

      do {
          // 4.1 解析当前 internal key
          if (!ParseKey(&ikey_)) return false;                // line 262
          //   internal key → ParsedInternalKey{user_key, sequence, type}

          // 4.2 检查 upper bound（Seek 的范围上界）
          if (user_key >= iterate_upper_bound_) break;         // line 276-282

          // 4.3 检查 prefix（prefix seek 模式）
          if (prefix && prefix_extractor_->Transform(user_key) != *prefix)
              break;                                           // line 285-289

          // ====== 可见性判断 ======
          if (IsVisible(ikey_.sequence, ts, &more_recent)) {   // line 301
              // ★ 此条目对当前 snapshot 可见

              // 4.4 跳过重复用户 key（如果正在 skipping）
              if (skipping_saved_key &&
                  CompareKeyForSkip(ikey_.user_key, saved_key_.GetUserKey()) <=
  0) {
                  num_skipped++;  // 跳过一个被删除/已返回过的 key 的旧版本
              } else {
                  num_skipped = 0;
                  switch (ikey_.type) {
                  case kTypeDeletion:       // 删除标记
                      saved_key_.SetUserKey(ikey_.user_key, ...);
                      skipping_saved_key = true;  // 跳过此 key 的所有旧版本
                      break;

                  case kTypeValue:          // ★ 找到了！这就是要返回的值
                      saved_key_.SetUserKey(ikey_.user_key, ...);
                      // Range Delete 检查
                      if (!range_del_agg_.ShouldDelete(ikey_, ...)) {
                          valid_ = true;
                          return true;      // ← 返回给用户
                      }
                      break;

                  case kTypeMerge:          // 遇到 Merge 操作
                      saved_key_.SetUserKey(ikey_.user_key, ...);
                      return MergeValuesNewToOld(); // 进入 Merge 状态机
                      //   ↓ 见 Step 4a
                  }
              }
          } else {
              // 不可见 (sequence > snapshot 或 timestamp 不匹配)
              // 该 key 是 "recent"，inserted after our snapshot
              num_skipped++;
          }

          // 4.5 Reseek 优化：如果连续跳过太多，用 Seek 跳跃
          if (num_skipped > max_skip_ && !reseek_done) {
              num_skipped = 0;
              reseek_done = true;
              // 构造: saved_key_ + sequence=0 + kTypeDeletion
              AppendInternalKey(&last_key,
                  ParsedInternalKey(saved_key_.GetUserKey(), 0, kTypeDeletion));
              iter_.Seek(last_key);                           // line 517
              //  直接跳到该 user_key 的最旧版本（seq=0），跳过中间所有版本
          } else {
              iter_.Next();                                    // line 520
              //  普通前进到 MergingIterator 的下一个最小 key
          }
      } while (iter_.Valid());

      valid_ = false;  // 遍历完所有数据，没找到
      return iter_.status().ok();
  }

  4a. MergeValuesNewToOld() — Merge 操作的状态机 (db/db_iter.cc:535-646)

  bool DBIter::MergeValuesNewToOld() {
      merge_context_.Clear();
      merge_context_.PushOperand(iter_.value(), ...);  // 第一个 merge 操作数

      ParsedInternalKey ikey;
      for (iter_.Next(); iter_.Valid(); iter_.Next()) {
          ParseKey(&ikey);

          if (!user_comparator_.Equal(ikey.user_key, saved_key_.GetUserKey())) {
              break;  // 到了下一个 user key，停止收集
          }

          switch (ikey.type) {
          case kTypeDeletion:
              // 被删除了 → 丢弃所有 merge 操作数，iter_ 前进
              iter_.Next();
              break;  // 循环结束

          case kTypeValue:
              // 找到 base value → 执行最终 merge
              Merge(&val, ikey.user_key);
              //   ↓ MergeHelper::TimedFullMerge(merge_operator_, user_key,
              //           &val, merge_context_->GetOperands(), &saved_value_, 
  ...)
              iter_.Next();
              return true;

          case kTypeMerge:
              // 又一个 merge → 收集操作数，继续
              merge_context_.PushOperand(iter_.value(), ...);
              break;
          }
      }

      // 到了 user key 边界，没有找到 base value
      // 用 nullptr 作为 base 执行最终 merge
      Merge(nullptr, saved_key_.GetUserKey());
      return true;
  }

  3.2 MergingIterator::Next() (table/merging_iterator.cc:153-184)

  void MergingIterator::Next() {
      // 如果方向不一致，先切换所有非 current_ 的子迭代器
      if (direction_ != kForward) {
          SwitchToForward();              // line 161
          //  对每个不是 current_ 的 child:
          //    child.Seek(current_->key()) → 如果等于则 child.Next()
          //  将所有 child 重新加入最小堆
      }

      // current_ 是最小堆的堆顶
      current_->Next();                    // line 171 —— 前进当前子迭代器

      if (current_->Valid()) {
          minHeap_.replace_top(current_);  // 子迭代器仍有效 → 替换堆顶
      } else {
          minHeap_.pop();                  // 子迭代器失效 → 从堆中移除
      }

      current_ = CurrentForward();         // 新的堆顶 = 全局下一个最小 key
  }

  3.5 DBIter::FindValueForCurrentKey() — 从旧到新扫描 (db/db_iter.cc:820-1000)

  Prev 的难点：内部数据按 seqno 降序排列（新的在前），但 Prev 需要找到每个用户
  key 的最新可见版本。所以它需要扫描到 seqno
  最小的版本（最旧），同时记录途中遇到的最新 Put/Delete：

  bool DBIter::FindValueForCurrentKey() {
      merge_context_.Clear();
      ValueType last_not_merge_type = kTypeDeletion;
      size_t num_skipped = 0;

      // 从当前位置向后扫描（seqno 变小，数据变旧），收集同一 user key 的版本
      while (iter_.Valid()) {
          ParsedInternalKey ikey;
          ParseKey(&ikey);

          // 遇到不同的 user key 或不可见 → 停止
          if (!IsVisible(ikey.sequence, ts) ||
              !user_comparator_.Equal(ikey.user_key, saved_key_.GetUserKey())) {
              break;
          }

          // Reseek 优化：跳过的 key 太多 → 用 Seek() 重新定位
          if (num_skipped >= max_skip_) {
              return FindValueForCurrentKeyUsingSeek();
          }

          switch (ikey.type) {
          case kTypeValue:
              pinned_value_ = iter_.value();        // ★ 记录最新看到的 Put
              merge_context_.Clear();               // 清空旧的 merge 操作数
              last_not_merge_type = kTypeValue;
              break;
          case kTypeDeletion:
              merge_context_.Clear();               // 遇到 Delete → 清空
              last_not_merge_type = kTypeDeletion;
              break;
          case kTypeMerge:
              // 按从旧到新的顺序压入操作数（Prev 方向是旧的在前）
              merge_context_.PushOperandBack(iter_.value(), ...);
              break;
          }

          iter_.Prev();  // 继续向更旧的方向移动
          num_skipped++;
      }

      // 扫描完毕，根据收集到的信息确定最终值：
      switch (last_key_entry_type) {
      case kTypeDeletion:
          valid_ = false;           // 被删除了
          return true;
      case kTypeMerge:
          // 用最新看到的非 merge 值（或 null）作为 base，执行 merge
          if (last_not_merge_type == kTypeValue)
              Merge(&pinned_value_, saved_key_.GetUserKey());
          else
              Merge(nullptr, saved_key_.GetUserKey());
          return true;
      case kTypeValue:
          valid_ = true;            // pinned_value_ 已经是最新的值
          return true;
      }
  }

  假设数据状态：

  IndexBlock Hash Search 中桶内二分查找的原理解析

  一、核心问题

  你的问题可以拆成两个：
  1. Hash 桶内的 block 信息是有序的吗？
  2. 为什么可以二分查找？

  简短回答：是的，同一个 hash 桶内的 block IDs 是按 升序排列的，而且每个 block
  在 Index Block 中都有对应的 restart point（完整 key），所以可以直接对 block
  进行二分查找。

  ---
  二、Hash Index 的整体结构

  RocksDB 的 Hash Search Index 由三部分组成：

  SST File
  ├── Data Blocks (数据块)
  ├── Index Block (索引块)
  │   ├── restart point 0: key "apple"  → BlockHandle(offset=..., size=...)  ←
  block 0
  │   ├── restart point 1: key "banana" → BlockHandle(...)                   ←
  block 1
  │   ├── restart point 2: key "cherry" → BlockHandle(...)                   ←
  block 2
  │   ├── restart point 3: key "date"   → BlockHandle(...)                   ←
  block 3
  │   ├── ...
  │   └── restart point N: key "zebra"  → BlockHandle(...)                   ←
  block N
  │
  ├── Prefix Block (kHashIndexPrefixesBlock)
  │   └── 存储所有前缀的字符串列表: "a", "b", "c", "d", ..., "z"
  │
  └── Prefix Meta Block (kHashIndexPrefixesMetadataBlock)
      └── 每条记录: [prefix_size, entry_index, num_blocks]
          │              │             │             └── 这个前缀跨越了多少个
  index block
          │              │             └── 起始 block 在 Index Block 中的位置
          │              └── 前缀的字节大小
          └── example: [1, 0, 1]  代表 "a" 前缀从 block 0 开始，跨 1 个 block
                       [1, 1, 2]  代表 "b" 前缀从 block 1 开始，跨 2 个 block

  在 BlockPrefixIndex::Create() 中（block_prefix_index.cc:169-208），从 Prefix

      uint32_t num_buckets = prefixes_.size() + 1;

      // 将每个前缀哈希到一个桶，建立链表
      std::vector<PrefixRecord*> prefixes_per_bucket(num_buckets, nullptr);
      for (PrefixRecord* current : prefixes_) {
          uint32_t bucket = PrefixToBucket(current->prefix, num_buckets);
          //      = Hash(prefix) % num_buckets

          // ★ 关键优化：合并相邻的 block 范围
          PrefixRecord* prev = prefixes_per_bucket[bucket];
          if (prev) {
              auto distance = current->start_block - prev->end_block;
              if (distance <= 1) {
                  // 前缀的 block 范围"连续"或"紧邻" → 合并为一个大区间
                  prev->end_block = current->end_block;
                  prev->num_blocks = prev->end_block - prev->start_block + 1;
                  continue;  // 不创建新节点，合并到现有记录中
              }
          }
          // 无法合并 → 链到桶的最前面
          current->next = prev;                 // 链表头插法
          prefixes_per_bucket[bucket] = current;
      }

  这里的关键：如果两个不同前缀哈希到了同一个桶，且它们的 block 
  范围连续（distance ≤ 
  1），就直接合并为一个更大的区间。如果不连续，它们作为链表中不同的节点存在。

  Step 3: 输出有序的 block ID 数组

          if (num_blocks == 0) {
              buckets[i] = kNoneBlock;                 // 空桶
          } else if (num_blocks == 1) {
              buckets[i] = prefixes_per_bucket[i]->start_block;  // 单

              block_array_buffer[offset] = num_blocks;  // 第一项存数量

              auto current = prefixes_per_bucket[i];    // 链表头（最新的前缀）

                  // ★ 从 end_block 到 start_block 降序填充，但 last_block

                      last_block--;  // 指针前移

              }
          }

  关键分析：这个填充过程保证了 block IDs 的升序排列。

  举例：假设桶内有两个 PrefixRecord：
  - Record A (较新): start_block=6, end_block=10, num_blocks=5 (前缀 "x")
  - Record B (较旧): start_block=0, end_block=2, num_blocks=3 (前缀 "a")
  - 链表顺序: A → B (A 是头)

  填充过程：
  初始: last_block 指向 array[offset + 8]  (因为总共有 8 个 block)

  处理 Record A (end_block=10, start_block=6):
    iter=0: array[offset + 8] = 10,   last_block → offset + 7
    iter=1: array[offset + 7] = 9,    last_block → offset + 6
    iter=2: array[offset + 6] = 8,    last_block → offset + 5
    iter=3: array[offset + 5] = 7,    last_block → offset + 4
    iter=4: array[offset + 4] = 6,    last_block → offset + 3

  处理 Record B (end_block=2, start_block=0):
    iter=0: array[offset + 3] = 2,    last_block → offset + 2
    iter=1: array[offset + 2] = 1,    last_block → offset + 1
    iter=2: array[offset + 1] = 0,    last_block → offset + 0

  最终 array:
    [offset + 0] = num_blocks = 8
    [offset + 1] = 0      ← block B 开始
    [offset + 2] = 1
    [offset + 3] = 2      ← block B 结束
    [offset + 4] = 6      ← block A 开始 (注意有间隔 2→6)
    [offset + 5] = 7
    [offset + 6] = 8
    [offset + 7] = 9
    [offset + 8] = 10     ← block A 结束

  结果：block IDs 严格升序排列 [0, 1, 2, 6, 7, 8, 9, 10]！

  PrefixSeek() —— 哈希定位 + 桶内二分 (block.cc:851-873)

  bool IndexBlockIter::PrefixSeek(const Slice& target, uint32_t* index,
                                  bool* prefix_may_exist) {
      Slice seek_key = target;

      // Step 1: 哈希定位——提取 target 的前缀，找到对应的桶
      uint32_t* block_ids = nullptr;
      uint32_t num_blocks = prefix_index_->GetBlocks(target, &block_ids);
      //        ↓
      //  BlockPrefixIndex::GetBlocks() (block_prefix_index.cc:210-229):
      //    prefix = internal_prefix_extractor_->Transform(key)
      //    bucket = Hash(prefix) % num_buckets_
      //    从 buckets_[bucket] 获取 block_ids 数组（已排序）

      if (num_blocks == 0) {
          // 桶为空 → 该前缀不可能存在
          *prefix_may_exist = false;
          return false;
      } else {
          // Step 2: 在桶内的 block_ids 数组上二分查找
          return BinaryBlockIndexSeek(seek_key, block_ids, 0, num_blocks - 1,

  BinaryBlockIndexSeek() —— 对 block IDs 进行二分查找 (block.cc:769-848)

  bool IndexBlockIter::BinaryBlockIndexSeek(const Slice& target,
                                            uint32_t* block_ids,  // ★ 已排序的 
  block ID 数组
                                            uint32_t left, uint32_t right,
                                            uint32_t* index, ...) {

      while (left <= right) {
          uint32_t mid = (right + left) / 2;

          int cmp = CompareBlockKey(block_ids[mid], target);
          //        ↓
          //  CompareBlockKey(block_index, target) (block.cc:749-765):
          //    1. 根据 block_index 定位到 Index Block 中对应的 restart point
          //       region_offset = GetRestartPoint(block_index)
          //    2. 解码该 restart point 处的完整 key
          //    3. 与 target 比较
          //
          //    ★ 关键：Index Block 中的每个 restart point 存储了完整 key
          //       （非 delta 编码），所以可以直接对任意 block index 进行比较

          if (cmp < 0) {
              left = mid + 1;    // target > mid → 去右边找
          } else {
              if (left == right) break;
              right = mid;       // target ≤ mid → 去左边找（包含 mid）
          }

  │ Block         │ restart point 对应一个 data block 的分隔 key。block ID  │

  │  block IDs    │ 范围。因此 block IDs 与 key 的大小关系是单调递增的。    │
  │ 有序          │                                                         │
  ├───────────────┼─────────────────────────────────────────────────────────┤

  七、总结

  桶内的 block 信息是有序的，因为：

  1. 构建时保证升序：BlockPrefixIndex::Builder::Finish() 从链表尾（block ID
  小）到链表头（block ID 大）依次填充，最终 block_array_buffer 中 block IDs
  严格升序。
  2. Index Block 的 restart point 天然有序：每个 restart point 存储完整 key，且
  key 随 block ID 单调递增。这使得 CompareBlockKey() 可以 O(1) 解码任意位置的
  key 进行比较。
  3. 二分查找的优势：无需线性扫描所有 block，桶内 O(log n)
  定位到具体的数据块。相比于全 Index Block 二分，Hash Index 将搜索空间从 N
  缩小到桶内的 n（通常 1~少数几个 block），大幅减少比较次数。
