  ---
  Speedb Hash Sorted Memtable 优化分析

  一、概述

  Hash Sorted Memtable（代码中称为 HashSpdbRep / hash_spdb）是 Speedb
  团队开发的一种基于哈希表 + 排序向量的内存表实现。其核心设计目标是：

  - 并发读写支持（InsertConcurrently）
  - 优于 SkipList 的插入和点查性能
  - 比 RocksDB 原生 Hash Memtable（HashSkipList/HashLinkList）更好的迭代性能
  - 更低的内存占用

  原始 PR: #98 (初始实现)，由 Ayelet Shani (ayelet@speedb.io) 于 2021年8月提交。

  二、架构设计

  核心数据结构三件套

  ┌─────────────────────────────────────────────────────────┐
  │                    HashSpdbRep                           │
  │  ┌──────────────────────┐  ┌──────────────────────────┐ │
  │  │    SpdbHashTable      │  │  SpdbVectorContainer     │ │
  │  │  (bucket array)       │  │  (managed vector list)   │ │
  │  │                       │  │                          │ │
  │  │  [BucketHeader]       │  │  [SpdbVector]            │ │
  │  │  [BucketHeader]       │  │  [SpdbVector]            │ │
  │  │  [BucketHeader]  ...  │  │  [SpdbVector]  ...       │ │
  │  │                       │  │                          │ │
  │  │  Each bucket holds    │  │  Each vector holds       │ │
  │  │  sorted linked list   │  │  sorted array of keys    │ │
  │  │  of SpdbKeyHandle     │  │  (for iteration)         │ │
  │  └──────────────────────┘  └──────────────────────────┘ │
  └─────────────────────────────────────────────────────────┘

  数据流

  Insert(key)
      │
      ├──► SpdbHashTable::Add()
      │       ├── MurmurHash(user_key) → bucket index
      │       └── BucketHeader::Add()
      │             └── 按排序顺序插入链表 (WriteLock保护)
      │
      └──► SpdbVectorContainer::Insert()
              └── curr_vector->Add(key)  (无锁，atomic)
                    └── 若当前 vector 满 → 创建新 vector
                          └── notify sort_thread 进行后台排序

  三、逐模块实现逻辑

  1. SpdbHashTable + BucketHeader — 哈希索引层

  文件: memtable/hash_spdb_rep.cc:36-192

  - 哈希函数: 使用 MurmurHash 对 user_key（去除 timestamp）计算哈希值
  - 桶定位: hash % buckets_.size() 取模定位到具体桶
  - 桶内结构: 每个 BucketHeader 维护一个按 key 排序的单向链表，节点为
  SpdbKeyHandle
  - 并发控制: 每个桶有独立的 RWMutexWr
    - Add(): 写锁，遍历链表找到位置后插入，如果 key 已存在返回 false（去重）
    - Contains() / Get(): 读锁（当 memtable 非只读时需要）
    - 链表遍历利用排序特性提前终止（cmp_res > 0 时 break）

  关键优化: 桶内链表是有序的，因此查找可在遇到更大 key
  时提前终止，避免全桶扫描。

  2. SpdbVector + SpdbVectorContainer — 排序向量层

  文件: memtable/spdb_sorted_vector.h:29-259

  SpdbVector（单个向量）

  - 底层是 std::vector<const char*>，预分配固定大小 (switch_spdb_vector_limit_ =
  10000)
  - 插入阶段是无序的（纯 append），使用 atomic<size_t> n_elements_ 追踪位置
  - 懒排序: 在迭代器创建时才通过 Sort() 进行排序（std::sort），排序后标记
  sorted_ = true
  - 插入锁仅使用 RWMutexWr 保护，允许并发读取已排序的向量
  - 排序后变为不可变（immutable），后续插入流向新 vector

  SpdbVectorContainer（向量容器管理器）

  - 维护一个 std::list<SpdbVectorPtr>，所有激活的向量
  - curr_vector_: 当前接收新插入的向量（atomic 指针，无锁切换）
  - 后台排序线程: SortThread() 持续等待条件变量通知，对非当前向量调用 Sort()
    - 线程在构造时启动，在 MarkReadOnly() 时终止
  - iterator 创建: InitIterator() 创建新的空 vector
  作为当前写入目标，返回现有所有非空向量的迭代锚点列表

  3. SpdbVectorIterator — 迭代器层

  文件: memtable/spdb_sorted_vector.h:261-403

  - 维护一个 IterHeap（最小堆/最大堆，取决于方向），对多个 sorted vector 做归并
  - 每个 vector 内部已排序，通过二分查找 (std::lower_bound) 定位 seek 位置
  - 支持 Seek, SeekForPrev, SeekToFirst, SeekToLast, Next, Prev
  - 方向反转: ReverseDirection() 在 Next↔Prev 切换时重新定位

  4. HashSpdbRep — 主类

  文件: memtable/hash_spdb_rep.cc:402-451

  - 组合 SpdbHashTable（点查/去重）和 SpdbVectorContainer（迭代）
  - InsertKey: 先入哈希表（去重 + 排序链表），再入 VectorContainer
  - Contains: 委托给 SpdbHashTable::Contains()
  - Get: 委托给 SpdbHashTable::Get()，通过回调返回结果
  - GetIterator: 创建 SpdbVectorIterator 遍历所有排序向量

  5. HashSpdbRepFactory — 工厂类

  文件: memtable/hash_spdb_rep.cc:555-611

  - 配置选项: hash_bucket_count（默认 400000）、use_merge（默认 true）
  - 关键特性:
    - IsInsertConcurrentlySupported() = true — 支持并发插入
    - CanHandleDuplicatedKey() = true — 可处理重复 key（哈希表去重）
    - IsRefreshIterSupported() = false — 不支持刷新迭代器
  - PreCreateMemTableRep / PostCreateMemTableRep: 支持异步 memtable 切换
    - Pre: 仅分配哈希表（无 comparator/allocator）
    - Post: 设置 comparator 和 allocator，创建 VectorContainer

  四、性能优化要点

  ┌──────────┬─────────────────────────────────────┐
  │  优化点  │              实现方式               │
  ├──────────┼─────────────────────────────────────┤
  │ 并发插入 │ 每桶独立锁 + vector 无锁 append     │
  ├──────────┼─────────────────────────────────────┤
  │ 后台排序 │ 独立排序线程，插入不阻塞在排序上    │
  ├──────────┼─────────────────────────────────────┤
  │ 懒排序   │ 只在需要迭代时才排序                │
  ├──────────┼─────────────────────────────────────┤
  │ 二分查找 │ 排序后的 vector 支持 O(log n) seek  │
  ├──────────┼─────────────────────────────────────┤
  │ 堆归并   │ 多 vector 通过最小堆/最大堆高效归并 │
  ├──────────┼─────────────────────────────────────┤
  │ 提前终止 │ 桶内有序链表在比较结果 > 0 时 break │
  └──────────┴─────────────────────────────────────┘

  补丁包含的核心功能

  1. SpdbHashTable — 基于 MurmurHash
  的固定桶数组，每桶内维护有序单向链表，支持并发读写
  2. SpdbVector + SpdbVectorContainer —
  管理多个排序向量，后台线程懒排序，支持多路归并迭代
  3. SpdbVectorIterator — 基于 BinaryHeap 的多向量归并迭代器，支持双向遍历
  4. HashSpdbRepFactory — 工厂类，配置项 bucket_count（默认 1000000）和
  use_merge（默认 true）

  使用方式

  程序化创建：
  options.memtable_factory.reset(NewHashSpdbRepFactory(400000, true));

  配置字符串：
  memtable_factory=hash_spdb:400000

● 性能测试结果

  测试环境

  - CPU: aarch64, RocksDB v6.26.1, 单线程/4线程
  - 数据: 100万~200万条 KV (key=16B, value=100B)，无压缩

  单线程性能对比（两轮平均）

  ┌───────────────────────┬─────────────────┬─────────────┬───────┐
  │         场景          │ SkipList (基线) │  HashSpdb   │ 提升  │
  ├───────────────────────┼─────────────────┼─────────────┼───────┤
  │ fillrandom (写入)     │ 320K ops/s      │ 645K ops/s  │ +101% │
  ├───────────────────────┼─────────────────┼─────────────┼───────┤
  │ readrandom (点查)     │ 208K ops/s      │ 259K ops/s  │ +24%  │
  ├───────────────────────┼─────────────────┼─────────────┼───────┤
  │ seekrandom (范围扫描) │ 96.5K ops/s     │ 97.1K ops/s │ +0.7% │
  ├───────────────────────┼─────────────────┼─────────────┼───────┤
  │ overwrite (更新)      │ 333K ops/s      │ 654K ops/s  │ +97%  │
  └───────────────────────┴─────────────────┴─────────────┴───────┘

  多线程性能对比（4 线程）

  ┌──────────────────┬────────────┬────────────┬───────┐
  │       场景       │  SkipList  │  HashSpdb  │ 提升  │
  ├──────────────────┼────────────┼────────────┼───────┤
  │ fillrandom       │ 399K ops/s │ 436K ops/s │ +9.3% │
  ├──────────────────┼────────────┼────────────┼───────┤
  │ readwhilewriting │ 345K ops/s │ 428K ops/s │ +24%  │
  └──────────────────┴────────────┴────────────┴───────┘

  结论

  - 写入性能: hash_spdb 单线程写入提升约 2 倍（+101%），主要得益于其无锁 vector
  append + 后台排序的设计
  - 点查性能: 提升约 24%，得益于哈希桶 O(1) 定位 + 桶内有序链表二分查找
  - 范围扫描: 与 SkipList 基本持平（+0.7%），多 vector 归并的开销与跳跃表相当
  - 并发写入: 4 线程下提升收窄至 9%，说明桶级锁竞争在高并发下成为瓶颈，但仍优于
  SkipList
  - 混合负载: readwhilewriting 提升 24%，读写并发优势明显

❯ rocksdb中random seek和random read的区别是什么                                 

  Thought for 10s (ctrl+o to expand)

● RocksDB 中 random read 与 seek random 的区别

  random read（随机点读）

  底层调用: DB::Get(key)

  MemTable → Immutable MemTables → SST Files (逐层)
    │                │                    │
    └─ 哈希桶定位      └─ 二分查找          └─ 索引块二分 + Bloom Filter 过滤

  - 只返回精确匹配的 key-value
  - 可以利用 Bloom Filter 快速跳过不存在的 key
  - 复杂度: O(1) ~ O(log N)，非常高效

  seek random（随机定位 + 扫描）

  底层调用: DB::NewIterator()->Seek(key) → 可选 Next() N 次

    创建 MergingIterator（合并所有层的迭代器）
         │
    在各层 MemTable/SST 中定位到 >= key 的位置
         │
    用 最小堆 归并排序各层的结果
         │
    返回第一个 >= key 的 entry → Next() → Next() ...

  - 返回第一个 >= key 的 entry（不要求精确匹配）
  - 需要构建多层归并迭代器（MergingIterator + MinHeap）
  - 不能使用 Bloom Filter 跳过（因为即使 key 不存在，也要找到下一个 >= 的 key）
  - 复杂度: O(log N × 层数)，比点读重得多

  对比

  ┌──────────────┬──────────────────────┬───────────────────────┐
  │              │     random read      │      seek random      │
  ├──────────────┼──────────────────────┼───────────────────────┤
  │ API          │ Get(key)             │ Seek(key) + Next()    │
  ├──────────────┼──────────────────────┼───────────────────────┤
  │ 匹配         │ 精确匹配             │ >= key 即可           │
  ├──────────────┼──────────────────────┼───────────────────────┤
  │ Bloom Filter │ ✅ 可用              │ ❌ 不可用             │
  ├──────────────┼──────────────────────┼───────────────────────┤
  │ 迭代器开销   │ 无                   │ 多层级 MinHeap 归并   │
  ├──────────────┼──────────────────────┼───────────────────────┤
  │ 典型用时     │ ~3-5 μs              │ ~10-15 μs             │
  ├──────────────┼──────────────────────┼───────────────────────┤
  │ YCSB 场景    │ Workload C (100% 读) │ Workload E (扫描密集) │
  └──────────────┴──────────────────────┴───────────────────────┘

  这对 hash_spdb 的影响

  在 YCSB 测试中：
  - Workload C (100% 纯点读): hash_spdb 比 skip_list 快 +13% — 哈希桶 O(1)
  定位优势
  - Workload E (95% 扫描): hash_spdb 比 skip_list 慢 95% — 每个 seek
  需要重建多个 SpdbVector 的最小堆归并，而 skip_list 天然有序，seek
  后直接遍历即可

❯ random seek和scan的区别是什么                                                 

  Thought for 2s (ctrl+o to expand)

● random seek vs scan 的区别

  random seek（随机定位）

  示例: 在 100万 key 中，随机找一个 key 的"附近位置"并读少量数据

  过程：
  1. 随机选择一个 key
  2. Seek(target) → 定位到 >= target 的第一个 entry
  3. Next() → 读取后续 N 个 entry（通常 N=10~100）
  4. 销毁迭代器

  Seek("user:500123") → [user:500123, user:500124, ... user:500132]
                         ↑ 定位                ↑ Next() × 10

  关键特征：
  - 每次 seek 创建全新迭代器
  - 从头构建 MinHeap 归并各层
  - 只读少量数据后立即销毁
  - 下一个 seek 又是完全不同的 key 位置

  scan（范围扫描）

  示例: 从 start_key 开始，连续读完一个范围

  过程：
  1. 创建一个迭代器
  2. Seek(start_key) → 定位起点
  3. Next() → 持续读到 range_size 条数据（通常 100~10000）
  4. 销毁迭代器

  Seek("user:100000") → [user:100000, user:100001, ... user:101000]
                         ↑ 定位        ↑ Next() × 1000

  关键特征：
  - 迭代器创建一次
  - 每个 seek 读取的数据量大得多
  - 数据是连续范围，读取有空间局部性

  本质区别

  ┌──────────────────┬─────────────────────┬────────────────────┐
  │                  │     random seek     │        scan        │
  ├──────────────────┼─────────────────────┼────────────────────┤
  │ 每次 seek 读多少 │ 少（10~100 条）     │ 多（100~10000 条） │
  ├──────────────────┼─────────────────────┼────────────────────┤
  │ 迭代器创建频率   │ 每次 seek 新建      │ 每次 scan 新建一次 │
  ├──────────────────┼─────────────────────┼────────────────────┤
  │ 数据连续性       │ 随机跳跃            │ 连续递增           │
  ├──────────────────┼─────────────────────┼────────────────────┤
  │ 开销分布         │ 创建/销毁开销占比大 │ Next() 开销占比大  │
  ├──────────────────┼─────────────────────┼────────────────────┤
  │ Cache 友好度     │ 差（随机位置）      │ 好（连续范围）     │
  └──────────────────┴─────────────────────┴────────────────────┘

  对 hash_spdb 的影响

  random seek:
    每个 seek → 新建 SpdbVectorIterator → 对每个 SpdbVector 做 Sort() +
  lower_bound →
    构建 MinHeap → 读 10 条 → 销毁
    问题: seek 开销远大于实际读数据开销

  scan:
    创建迭代器一次 → seek 一次 → Next() × 1000 → 销毁
    问题: Next() 在 MinHeap 上做 replace_top() 开销累积

  两者 hash_spdb 都表现不佳，因为核心瓶颈相同——多向量归并的 MinHeap 开销是
  skip_list 不具备的。YCSB Workload E 用的是 scanproportion=0.95, 
  maxscanlength=100，属于 scan 场景。

  ---
  不同场景的配置建议

  场景 1: 写密集型（时序数据、日志入库）

  memtable_factory=hash_spdb:200000

  - 降低 bucket_count（20 万）：减少桶数组内存开销
  - 写多读少的场景，桶内链表比哈希定位的开销差异不敏感
  - 重点是利用无锁 vector append 的写入优势

  场景 2: 点查型（KV 缓存、Session Store）

  memtable_factory=hash_spdb:800000

  - 提高 bucket_count（80 万）：桶内链表更短，提升点查速度
  - 在 memtable 数据量较大时（64MB write_buffer），均匀分布下每桶 ~50 条
  - 点查 O(1) 定位 + 桶内短链表遍历，延迟更低

  场景 3: 混合 OLTP（YCSB A/F 类型）

  memtable_factory=hash_spdb:400000

  - 默认值（40 万）是最均衡的选择
  - 对 64MB write_buffer（约 50 万条 KV），每桶约 1~2 条
  - 兼顾写入和点查，对大多数场景友好

  场景 4: 大 value / 大 write_buffer

  # 若 write_buffer_size=256MB，预计 ~200万条 KV
  memtable_factory=hash_spdb:1000000

  - 数据量越大，越需要增大 bucket_count 避免桶内链表过长
  - 经验公式：bucket_count ≈ 预计最大条目数 / 5

  场景 5: 范围扫描场景 → 不推荐

  # 不应使用 hash_spdb，回退到 skip_list
  memtable_factory=skip_list

  ┌─────────────┬─────────────────────┬──────────────────────────────┬──────┐
  │    操作     │      SkipList       │           HashSpdb           │ 差距 │
  ├─────────────┼─────────────────────┼──────────────────────────────┼──────┤
  │ Seek 定位   │ ~18 次比较          │ 20×13 + 堆构建 ≈ 346 次比较  │ 19×  │
  ├─────────────┼─────────────────────┼──────────────────────────────┼──────┤
  │ 每次 Next() │ 1 次指针解引用      │ 1 次指针 + replace_top ~5    │ —    │
  │             │                     │ 次比较                       │      │
  ├─────────────┼─────────────────────┼──────────────────────────────┼──────┤
  │ 扫 500      │ 18 + 500 = 518      │ 346 + 2500 = ~2850 "单位"    │ 5.5× │
  │ 条合计      │ "单位"              │                              │      │
  └─────────────┴─────────────────────┴──────────────────────────────┴──────┘

  但实际慢了 19×，多出来的 ~3.5× 来自：

  隐藏开销

  1. 堆动态分配
     Reset() {
       iter_heap_.reset(new IterHeap(...))    ← 每次 Seek 都 new 一个堆对象
     }
     → 380 次 scan × heap allocation = 频繁内存分配

  2. 堆操作的缓存不友好
     SkipList: node → node->next → node->next  (连续指针追踪, L1 cache 友好)
     HashSpdb: replace_top → sift_down → 比较器 → 再比较 → (跨 vector 跳跃,
  cache miss)

  3. InternalKeyComparator 很重
     heap compare = InternalKeyComparator(user_key + seq + type)
     比 SkipList 的裸指针解引用重一个数量级

  火焰图上的表现

  SkipList scan 热点:                HashSpdb scan 热点:
                                     ████████████ IterHeap::replace_top (堆调整)
                                     ████████ IteratorComparator::operator()
  (比较)
                                     ██████ SpdbVector::Next (向量内指针)
                                     █████ SeekIter (二分 + 堆构建)
                                     ███ BinaryHeap 内存分配
  █ node->Next()   (几乎全部)
                                     ██ Sort() (若未排完)
  █ FindGreaterOrEqual (仅 seek 时)

  结论

  hash_spdb 不是为扫描设计的——它的架构取舍非常明确：

  ┌────────────┬──────────────────────┬──────────────────────────────┐
  │            │       SkipList       │           HashSpdb           │
  ├────────────┼──────────────────────┼──────────────────────────────┤
  │ 数据结构   │ 全局有序单向链表     │ N 个独立排序向量 + 哈希表    │
  ├────────────┼──────────────────────┼──────────────────────────────┤
  │ Seek       │ 跳表定位, O(log N)   │ N×二分 + 堆构建, O(N log M)  │
  ├────────────┼──────────────────────┼──────────────────────────────┤
  │ Next       │ 1 次指针解引用, O(1) │ replace_top 堆调整, O(log N) │
  ├────────────┼──────────────────────┼──────────────────────────────┤
  │ 扫描开销   │ Seek + 指针追逐      │ Seek + 每次 Next 都做堆操作  │
  ├────────────┼──────────────────────┼──────────────────────────────┤
  │ 内存分配   │ 无                   │ 每次 Seek new BinaryHeap     │
  ├────────────┼──────────────────────┼──────────────────────────────┤
  │ 缓存局部性 │ 极好 (单向链表)      │ 差 (堆跨向量跳跃)            │
  └────────────┴──────────────────────┴──────────────────────────────┘

  如果场景有 >10% 的扫描操作，应该用 SkipList。hash_spdb 只适合纯写入 + 
  点查场景。

  嵌套堆的叠加效应

  更隐蔽的开销是两层堆嵌套：

  DB 层 MergingIterator (MinHeap 合并多层)
    ├─ MemTable → SpdbVectorIterator (MinHeap 合并 20 个 vector)  ← 内层堆
    ├─ Imm MemTable 1 → 又一个 SpdbVectorIterator (又一个堆)      ← 又一个
    └─ SST 层 → BlockBasedTableIterator (二分定位)

  MergingIterator::Next():
    top_item = heap->top()           ← 外层堆顶
    top_item->iter->Next()           ← 触发内层 SpdbVectorIterator::Next()
      → replace_top() 内层堆调整     ← 内层 replace_top
    heap->replace_top()              ← 外层 replace_top (≈另一组比较)

  SkipList 没有内层堆——每个 layer 的 iterator 就是简单的跳表节点指针。Next()
  只是一次指针解引用。

  N 的物理意义

     MemTable (64MB, ~25万条 key @ 256B)
     ┌──────────────────────────────────────────────┐
     │  SpdbVector[0]   10000 条  ████████████████  │
     │  SpdbVector[1]   10000 条  ████████████████  │
     │  ...                                        │
     │  SpdbVector[24]  10000 条  ████████████████  │
     │  SpdbVector[25]  (当前写入)                  │
     └──────────────────────────────────────────────┘
           N = ceil(250000 / 10000) = 25 个 vector

  每次 scan: Seek → 25×lower_bound + 25×push → 堆构建
  每次 Next: replace_top → log₂(25)≈5层 → ~10次比较

  ---
  调大 limit 的收益递减

                  N     heap depth    Next 比较次数    Seek 比较次数
  limit=10000     25       5             ~10              ~350
  limit=20000     13       4             ~8               ~170
  limit=50000      5       3             ~6               ~65
  limit=100000     3       2             ~4               ~30
  limit=250000     1       0             0                ~13  ←
  归并退化，等于单vector二分

  扫描收益: limit 从 1 万 → 5 万，Next 比较从 ~10 降到 ~6，Seek 从 ~350 降到
  ~65，约 5× 改善。但仍远不及 SkipList 的 0 比较。

  但不会达到 SkipList 的水平，因为即使 N=1，Seek 仍需
  std::lower_bound（二分查找），扫描仍需遍历所有条目。

  limit=250000:  整个 memtable 一个 vector → 插入完毕才能用 → 退化为 VectorRep

● 结论：完全可以实现，且不需要任何代码改动

  原理

  RocksDB 的 memtable 类型是打开时绑定的，每次 RocksDB::Open() 时从
  Options.memtable_factory 读取。YCSB 每个 run 命令启动一个独立 JVM 
  进程，各自打开独立的 RocksDB 实例，因此每个 workload 可以有不同的 memtable
  配置。

  YCSB run workload A → RocksDB::Open() → Options{mf=hash_spdb} → HashSpdbRep
  YCSB run workload E → RocksDB::Open() → Options{mf=skip_list} → SkipListRep
                        ↑ 读的是同一份 SST 数据，memtable 仅在当前进程中生效

  数据是共享的：load 阶段写入的 SST 文件存在同一个 --db 目录下，run 阶段各
  workload 读的都是这些文件。

  ---
  直接可用的脚本

  #!/bin/bash
  export
  JAVA_HOME=/usr/lib/jvm/java-1.8.0-openjdk-1.8.0.462.b08-4.oe2403sp2.aarch64
  export PATH=$JAVA_HOME/bin:$PATH

  DB_DIR=/tmp/ycsb_best_of_both
  rm -rf $DB_DIR
  YCSB=/data/zyue/YCSB
  REC=1000000

  # ═══════════════════════════════════════════════════
  #  Load 阶段：hash_spdb 写入快 2 倍
  # ═══════════════════════════════════════════════════
  echo "=== LOAD with hash_spdb ==="
  ${YCSB}/bin/ycsb.sh load rocksdb -s \
    -P workloads/workloada \
    -p recordcount=${REC} \
    -p rocksdb.dir=${DB_DIR} \
    -p rocksdb.memtable=hash_spdb

  # ═══════════════════════════════════════════════════
  #  Run: Workload A/B/C/D/F → hash_spdb (点查/混合)
  # ═══════════════════════════════════════════════════
  for W in a b c d f; do
    echo "=== Run Workload ${W^^} with hash_spdb ==="
    ${YCSB}/bin/ycsb.sh run rocksdb -s \
      -P workloads/workload${W} \
      -p recordcount=${REC} -p operationcount=${REC} \
      -p rocksdb.dir=${DB_DIR} \
      -p rocksdb.memtable=hash_spdb
  done

  # ═══════════════════════════════════════════════════
  #  Run: Workload E → skip_list (扫描密集)
  # ═══════════════════════════════════════════════════
  echo "=== Run Workload E with skip_list ==="
  ${YCSB}/bin/ycsb.sh run rocksdb -s \
    -P workloads/workloade \
    -p recordcount=${REC} -p operationcount=${REC} \
    -p rocksdb.dir=${DB_DIR} \
    -p rocksdb.memtable=skip_list

  ---
  为什么这是最优策略

  Load (Write):    hash_spdb  →  写入吞吐翻倍, 加载 100万条快 ~50%

  Run A (50R/50W): hash_spdb  →  +31% 读写混合
  Run B (95R/5W):  hash_spdb  →  +23% 读密集
  Run C (100R):    hash_spdb  →  +13% 纯点读
  Run D (95R/5I):  hash_spdb  →  +28% 读+插入
  Run E (95S/5I):  skip_list  →  避免 scan 性能退化 19×
  Run F (50R/50RM): hash_spdb  →  +31% 读写改

  没有任何 trade-off：每个 workload 都用最适合的 memtable。
